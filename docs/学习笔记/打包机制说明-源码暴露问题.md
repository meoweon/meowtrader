# PyInstaller 打包源码暴露问题

## 问题说明

### `vendor/` 目录源码暴露

`vendor/` 目录通过 `--add-data` 被**原样复制**到打包结果中，导致：

- ✅ `.py` 源代码文件完全暴露在 `_internal/vendor/` 目录中
- ✅ 用户可以直接查看、修改源码
- ❌ **没有任何源码保护**

### 为什么 `vendor/` 必须用 `--add-data`？

**原因**：

1. `vendor/` 目录不在标准的 Python 路径中
   - 不在 `site-packages/`
   - 不在 `sys.path` 中（通过 `bootstrap.py` 动态添加）

2. PyInstaller 无法自动发现这些模块
   - PyInstaller 只分析标准的 Python 导入
   - 无法知道 `vendor/` 目录的存在

3. 运行时需要访问这些模块
   - `from vnpy.trader import ...` 需要找到 `vendor/vnpy/`
   - `from vnpy_okx import ...` 需要找到 `vendor/gateways/vnpy_okx/`

**解决方案**：使用 `--add-data` 将整个目录复制到打包结果中。

## `core/` 和 `app/` 的情况

### 为什么它们不在 `_internal/` 中？

**原因**：

1. **自动收集**：PyInstaller 通过分析 `app/desktop/main.py` 的导入自动发现
   - `from meowtrader.core import ...` → 自动找到 `core/` 目录
   - `app/desktop/main.py` 是入口脚本，会被直接打包

2. **打包位置**：被打包到 `base_library.zip` 中（已编译为 `.pyc`）
   - 不在 `_internal/` 目录结构中
   - 但功能完全正常

3. **源码保护**：`.pyc` 在压缩包中，比直接暴露 `.py` 稍好（但仍可反编译）

### `core/` 和 `app/` 的作用

#### `core/` - 产品层封装

**作用**：封装 vnpy，提供统一的产品层 API

- `ProductEngine`：封装 vnpy MainEngine，提供稳定接口
- `ConfigManager`：配置文件管理和加载
- `RuntimeManager`：运行时环境管理（路径配置、日志等）
- `ModuleRegistry`：模块注册表（Gateway/App 清单）

**代码量**：较少，主要是封装逻辑

#### `app/` - 启动入口

**作用**：提供不同的启动方式

- `app/desktop/main.py`：桌面客户端入口（GUI 模式）
- `app/server/main.py`：服务端入口（无 UI，运行策略）
- `app/web/main.py`：Web 服务入口（WebTrader）

**代码量**：很少，主要是初始化代码

### 为什么之前没有 `core` 和 `app` 也能运行？

**答案**：它们被打包了，只是不在目录结构中

- `core` 和 `app` 的 `.pyc` 文件在 `base_library.zip` 中
- Python 运行时从压缩包加载这些模块
- 功能完全正常，只是看不到目录结构

## 源码保护方案

### 方案 1：使用 Nuitka（推荐，真正的编译保护）

Nuitka 将 Python 编译为 C++，再编译为机器码：

```bash
python -m nuitka --standalone app/desktop/main.py
```

**优点**：
- ✅ **真正的编译保护**（机器码，难以逆向）
- ✅ 性能更好（编译后的代码）
- ✅ 源码不可见

**缺点**：
- 打包时间更长
- 体积可能更大
- 需要 C++ 编译器

**项目支持**：`packaging/nuitka/` 目录已存在

### 方案 2：编译为 `.pyc` 后打包（部分保护）

在打包前，将 `.py` 编译为 `.pyc`，只打包 `.pyc`：

```python
import compileall
compileall.compile_dir("vendor", force=True, quiet=1)
# 然后只复制 .pyc 文件到临时目录，再打包
```

**问题**：
- ⚠️ `.pyc` 可以反编译回 `.py`（虽然需要工具）
- ⚠️ 不是真正的保护

### 方案 3：源码混淆（中等保护）

使用 PyArmor 混淆代码：

```bash
pyarmor gen --recursive vendor/
```

**问题**：
- ⚠️ 仍可能被破解
- ⚠️ 增加了破解难度，但不是完全保护

### 方案 4：只保护关键部分（实用方案）

**策略**：
- `vendor/`：开源代码，不需要保护
- 核心算法：放在 `extensions/strategies/` 中，使用 Nuitka 单独编译
- 业务逻辑：混淆或编译关键策略文件

## 当前项目的处理

### 设计理念

1. **vnpy 是开源的**：`vendor/vnpy/` 本身就是开源项目
2. **vendor 中的 Gateway/App 也是基于开源**：大部分来自 vnpy 社区
3. **真正的商业机密在策略**：应该在 `extensions/strategies/` 中保护

### 建议

- ✅ **保持当前方式**：`vendor/` 通过 `--add-data` 打包，源码暴露
- ✅ **策略层保护**：如果需要，对 `extensions/strategies/` 中的策略进行编译或混淆
- ✅ **考虑 Nuitka**：如果整体需要保护，可以迁移到 Nuitka

## 总结

| 目录 | 打包方式 | 源码暴露 | 是否需要保护 |
|------|---------|---------|------------|
| `vendor/` | `--add-data` | ✅ 完全暴露 | ❌ 开源代码，不需要 |
| `core/` | 自动收集 → `base_library.zip` | ⚠️ `.pyc` 可反编译 | ❌ 封装代码，不重要 |
| `app/` | 自动收集 → `base_library.zip` | ⚠️ `.pyc` 可反编译 | ❌ 启动入口，不重要 |
| `extensions/strategies/` | 需要单独处理 | - | ✅ **核心算法，需要保护** |

**关键点**：
- `vendor/` 是开源代码，暴露是正常的
- 真正的商业价值在**策略逻辑**（`extensions/strategies/`），应该保护这部分
- 如果需要整体保护，考虑使用 **Nuitka**
